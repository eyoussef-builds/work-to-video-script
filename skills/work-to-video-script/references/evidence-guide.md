# Evidence and screenshot decisions

## A bounded scan

Begin with the active task and its project root. Inspect scoped status/diffs, relevant commits, the accepted requirements and final state notes. Read the original proof for claims that matter: a test log for a count, a deployment receipt plus current read-only health/version check for deployment, and an actual provider/user-journey record for real delivery. A documentation sentence claiming “verified” is not by itself equivalent to the receipt.

Use connected history tools where available. Do not scrape the agent's internal databases, unrelated chats or inboxes to broaden coverage. If history is inaccessible or truncated, state the coverage boundary and use other available proof. Do not ask the user to resend information already available in the authorized project.

When multiple dates or revisions exist, identify which release each asset proves. A later screenshot can demonstrate today's result but cannot prove the clicks used to create it earlier. Recreated dialogue cards can paraphrase an actual decision; label them as paraphrases and retain the private source reference.

## Private ledger

| Field | Meaning |
| --- | --- |
| Claim ID | Stable identifier used by the storyboard |
| Narrative statement | The precise fact being narrated |
| Source | Private relative file, commit, task turn or accessible official page |
| Version/date | Which state the proof establishes |
| Level | Implemented / synthetic / provider / deployed / actual journey |
| Limit | What the source does not prove |
| Shot IDs | Safe images or planned captures supporting the claim |
| Publication review | Safe derivative available / needs redaction / not for publication |

Do not put secret values or unnecessary message bodies in the ledger. The ledger itself can contain sensitive paths and operational context; keep it private.

## Capture decision

1. Existing genuine image: inspect relevance, date, pixels and metadata; create a separate safe derivative as needed.
2. Missing read-only view: use authorized browser/app capture, preserving the user's selected browser and account. Show the actual application, not an invented interface.
3. View requires a mutation or recipient interaction: add it to the demo plan. Do not execute merely to fill the storyboard.
4. No capture capability: mark “capture needed” and describe the exact view. The screenshot pack remains partial.

Keep a screenshot index with shot ID, file, capture date if known, historical/current/illustrative status, visible claim, redactions and scene use. Link safe images in the storyboard so the reviewer can inspect them.

## Editing evidence

Use faithful crops, opaque redactions and captions to focus a screenshot. Do not generatively reconstruct hidden UI, alter status labels or insert successful replies. A diagram can explain an interaction, but must remain labeled explanatory artwork. Never infer consent, ownership, billing safety or a successful result from an illustration.

Review derivatives at readable size. Check terminals, browser chrome, notifications, URLs/query strings, keys, real users, emails, device paths, project IDs, image metadata and QR codes. Remove unnecessary raw captures from any public or shareable bundle. Do not claim a pattern scanner establishes that every sensitive pixel is absent.

## Useful honesty checks

- “I built it myself”: acknowledge owner verification/approval and other contributors where material.
- “It works”: specify the verified path and separate synthetic coverage from live behavior.
- “It is fast”: use observed end-to-end measurements, not a model-only timing or an accelerated edit.
- “It understands everything”: demonstrate a bounded useful example; retain limitations.
- “It is open source/free”: check actual repository visibility, license and usage dependencies.
- “It bypasses a platform limit”: correct the claim and show the actual consent/eligibility step.
- “Real recording”: distinguish historical screenshots, current captures, later demonstrations and illustrative graphics.
